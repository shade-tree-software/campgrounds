# EKKO Trips

A Flask web app for documenting family camping trips in an RV called "EKKO" and discovering new campgrounds.

## Project Memory (versioned, travels with the repo)

Claude Code's auto-memory normally lives outside the repo (under `~/.claude/projects/<encoded-path>/memory/`) and is per-machine — it does NOT follow a clone. This project keeps its memory **in-repo and git-tracked** so a fresh `git clone`/`pull` + starting Claude brings it down automatically, with no manual setup:

- **`.claude/memory/`** — the committed memory files (`MEMORY.md` index + per-fact `*.md`). This is the source of truth; commit changes to it like any other code.
- **`.claude/settings.json`** sets `autoMemoryDirectory` to a fixed `~/` path (`~/.claude/memory-links/ekko-campgrounds`). That setting only accepts an absolute/`~/` path (no repo-relative/`$VAR`), so it can't name the repo directly.
- **`.claude/sync-memory.sh`**, run from a committed `SessionStart` hook (which gets `$CLAUDE_PROJECT_DIR`), symlinks that fixed path to `<repo>/.claude/memory` — bridging the fixed `autoMemoryDirectory` to wherever the repo is cloned. It's idempotent, migrates any stray memory written before first wiring, and prints `MEMORY.md` to stdout on the wiring event (recall insurance, since hook-vs-load order isn't guaranteed).

Net effect: clone/pull + start Claude wires memory automatically; new memories Claude writes land in `.claude/memory/`, ready to commit. The only one-time, per-machine step is accepting Claude Code's folder-trust dialog (the security gate that lets committed hooks/settings run at all) — unavoidable for any repo. The legacy per-project store under `~/.claude/projects/.../memory/` is now orphaned and ignored; it can be deleted once in-repo recall is confirmed after a restart.

## Tech Stack

- **Backend:** Flask (Python) on port 5001, Flask-Login for auth, Pillow for EXIF
- **Frontend:** Server-side Jinja2 templates, Leaflet.js maps, vanilla JS (no framework)
- **Storage:** JSON files (no database) — `trip_data/trips.json`, `trip_data/captions.json`, `trip_data/photo_order.json`, `trip_data/photo_uploaders.json`, `trip_data/photo_favorites.json`, `trip_data/photo_people.json`, `trip_data/share_tokens.json`, `trip_data/access_log.jsonl`
- **Photos:** Saved to `photo_uploads/{trip_id}/{stay_idx}/` (campspots) and `photo_uploads/{trip_id}/events/{event_idx}/` (events) — a **sibling of `static/`, deliberately not inside it**. Served only through the login-gated `/photo/` and `/thumb/` routes (see "Photo System").
- **External APIs:** Open-Meteo (forecast + elevation), Nominatim (geocoding), Overpass (POI lookup), OSRM (driving routes, browser-side), RIDB + recreation.gov (federal availability), Textbelt (SMS)
- **Virtualenv:** `ekko_trips_venv/` (activate before running)

## Key Files

- `ekko_trips_app.py` — Main Flask app: routes, auth, photo endpoints, campground CRUD API, geocode proxy
- `trips.py` — Trip data CRUD, JSON persistence, trip parsing logic, location resolution via `_load_locations_by_id()`, photo index remapping on sort
- `weather_finder.py` — Forecast search engine behind the Weather Finder page and the `find_summer.py` CLI. Stdlib-only (no `requests`/`geopy`). Batches Open-Meteo forecast requests (comma-separated coordinate lists, one object per location), snaps coordinates to a ~11 km grid so campgrounds sharing a model cell share one fetch, and caches per-cell forecasts for an hour. **The cache is what makes the page usable:** Open-Meteo's free tier bills per LOCATION and allows 600/minute (measured: 600 OK, 800 → 429), so a 400-mile search (1,289 campgrounds) spends most of a minute's budget — without the cache, adjusting a threshold and re-searching would rate-limit almost every time. Cached cells don't compete for `FORECAST_BUDGET`, so an over-budget radius fills in across successive searches rather than being permanently clipped to the same points.
- `home.json` — Gitignored per-machine config. Required: `home_lat`, `home_long`, `home_altitude_meters`. Optional: `home_place_names` (see "Home Stays").
- `campgrounds.json` — Unified location database (~12,900 entries). Each entry has `id` (stable auto-incrementing int), `kind` ("campground" or "family"), `name`, `location` ("lat,lng"), `state`. Campground-kind also carries `elevation_meters`, `waterfront`, `waterfront_evidence`, `inclusion_evidence`, `ownership`, `website`, `note`, `phone`, `stays`. Family-kind may carry `driveway_location` ("lat,lng") used instead of `location` for stay-marker placement.
- `roadside.json` — Leg-stretch stops (small-town parks, roadside picnic areas, rest areas) — deliberately separate from overnight campgrounds. Rendered as their own toggleable overlay on the campground map, with admin CRUD inline on that map (no dedicated manage page). `_roadside_view()` projects the stored record into the map shape.
- `detect_people.py` — Offline batch scanner: finds photos with people in them (OpenCV YuNet face detection; tiny ONNX model auto-downloaded once to `trip_data/models/` with a pinned sha256) and writes `trip_data/photo_people.json` (`{photo_key: face_count}`, one entry per SCANNED photo — 0 means "looked, nobody there", absent means "not scanned yet", which is what makes re-runs incremental). The web app never imports cv2 — it only reads the JSON (`people` flag in `_collect_photo_pool()`, ranked by the poster's hero deck). **Run it where the full photo library lives** (PA via an interactive login: `pip install --user opencv-python-headless`, then `python3 detect_people.py`; or locally after `./sync-from-pa.sh --photos`) — this machine holds only a partial photo mirror, which is also why `--prune` is off by default (pruning against a partial mirror would delete the records for every photo the machine doesn't have). Faces are the signal, so a person photographed from behind or at great distance won't register; that's acceptable because a false negative just leaves the photo in the general pool, and a false positive merely promotes a photo that was otherwise a coin flip. Verified on trip 92 (70 photos, 38 flagged, spot-checked clean, ~0.2 s/photo).
- `ridb/fetch_facility.py` — recreation.gov / RIDB client: `search_facilities`, `fetch_facility`, `availability_matrix`, `DEFAULT_FIT_FT`. RIDB supplies the campsite catalog (so sites can be filtered to ones EKKO fits); the recreation.gov calendar supplies live availability. Needs `RIDB_API_KEY`.
- `static/map-picker.js` — Shared map picker popup factory (`createMapPicker()`) used by campground manage and event location picker
- `static/map-picker.css` — Shared map picker styles (positioning, resize handles, geocode search dropdown)

The muted-tile filter is applied per-tile (`.leaflet-tile`), the combination verified in print at all four sizes.

## Architecture

### Trip ID vs Display Number

Trips have two distinct identifiers:
- **`id`** — Permanent, auto-incrementing integer. Used for URLs (`/trips/42`), photo directory paths, API routes, and all internal references. Never changes once assigned.
- **`number`** — Computed dynamically in `_load_trips_json()` based on chronological sort position. Used only for display ("Trip 5: ..."). Automatically adjusts when trips are added/removed without renumbering stored data.

### Trip Types

- **Empty trips** have no campspots or events. New trips are created empty. Summary defaults to "New Trip". They have no date range and are excluded from calendar dots and header day trip count but appear in the list view.
- **Overnight trips** have at least one campspot. Header stats show overnight trip count and total nights.
- **Day trips** have only events (no campspots). A trip survives deletion of its last campspot if it still has events. Date range is derived from events when no campspots exist. Summary falls back to trip note or "Events Only".

### Home Stays

A **home stay** is a night at the family's own house rather than a campsite. Home is not a `campgrounds.json` entry — it's recorded like a hotel would be: `campground_id: null` plus a free-text `custom_place`. A trip whose campspots are *all* home stays gets `home_only: true` and is hidden from the trips map, calendar, list and landing-page photos (admins still see it), and dropped from the stats entirely.

`trips.is_home_stay(stay)` is the single rule, and `trips.camping_nights(trip)` (`total_nights` minus home stays) is how any nights aggregate must be computed — the stats hero, the Nights-by-Year chart, and the site header all go through it so they can't disagree. A mixed trip (home for a few nights mid-trip, then back out) is the only case where the two differ; there are none in the data today, which is exactly why the distinction is easy to lose.

**Because a false positive is expensive and silent** — it makes a real trip vanish from every public surface — matching is deliberately conservative:
1. **A stay with a non-null `campground_id` is never home.** Home is always free text, so this rules out every campground-name collision. It matters: the marker below is a *substring* test, and `"basset"` is a substring of **"Bassett City Park"** (id 2771, a real municipal campground in NE). Without this guard, camping there would silently bury the trip.
2. If `home.json` defines `home_place_names` (a list of strings), the free-text place must match one **exactly** (case- and whitespace-insensitive). This also closes free-text collisions (an Airbnb named "Bassett Inn").
3. Otherwise it falls back to the legacy `"basset"` substring. The fallback exists so a host whose `home.json` hasn't been updated keeps working — **if matching silently stopped, the home trips would become publicly visible**, which is the failure mode worth guarding.

The names live in gitignored config rather than in code because **this repo is public and the home place name is a street address** — hardcoding it would publish it. Adding `home_place_names` to a host's `home.json` is optional and per-machine; without it that host just runs the legacy path.

### Data Model

- Trips contain campspots and events. Campspots sort by start date, events by date; the timeline merges both. New campspots/events default their date to the trip's first campspot start date.
- **Campspots** reference a location via `campground_id` (int, or null with free-text `custom_place` for hotels/Airbnbs). `_make_trip()` materializes a display-only `place` string from `campground_id` → name (with `custom_place` fallback). Optional `campsite_location` ("lat,lng") overrides the campground's listed coords when the listed coords are the office/entrance and the actual campsite is meaningfully offset. `enrich_trip_locations()` prefers `campsite_location` when set.
- **Events** have optional `end_date` and `location` (lat,lng). Plotted as gold stars on trip detail / gold dots on the main map. The event-location picker is the shared map picker without elevation lookup; the trip-detail stay edit form reuses it via `pickerTarget` for the "Pick on Map" button.
- **Family visits** are events with a non-null `family_id` (referencing a `kind: "family"` entry in `campgrounds.json`). `_make_trip()` materializes a `family_visit` label from `family_id`. Location auto-set from the family entry (preferring `driveway_location`). Rendered as red house icons (z-index 850) with salmon-toned cards and a simplified edit form. `onFamilyVisitChange` only overwrites the event `name` when it looks auto-filled (blank or matches any family label), so a custom name survives a family-location change. Proximity family markers are suppressed for locations that already have a family-visit on the trip.

### Auth & Admin Protection

Login is global via `_require_login_globally()` (registered as `before_request`). Exempt endpoints: `login`, `service_worker`, `offline`, `sw_reset`, `share_login`, `serve_tile`, `serve_pmtiles`, and `static` — **except** `static` requests under `uploads/`, which are refused outright (see "Photo System"). `_require_admin()` guards all mutation endpoints. Templates condition edit controls on the `is_admin` Jinja var / `IS_ADMIN` JS constant; drag-drop is fully disabled for non-admins.

`?next=` survives the login detour: `_require_login_globally()` sets it from `request.full_path` (so a query string like `?color=climate` is preserved), the login form posts back to that same URL, and the POST handler redirects through `_safe_next()`, which restricts the target to a same-site path so it can't become an open redirect.

**Roles.** Accounts live in `users.json` (`{username: {password_hash, is_admin, can_upload, can_view_campgrounds}}`, hashed via `werkzeug.security.generate_password_hash`). Beyond admin there are two narrower capabilities:
- `can_upload` — may POST photos and edit captions on photos they uploaded (ownership tracked in `trip_data/photo_uploaders.json`, keyed identically to captions). Gated by `_require_uploader_or_admin()` + `_can_edit_photo()`. Deleting and reordering stay admin-only. Admins always pass.
- `can_view_campgrounds` — defaults true; clearing it makes a **Trips-only** user. `_require_campground_view_page()` redirects them off Campgrounds-section pages and `_require_campground_view_api()` 403s the matching APIs; the nav group and the phone tab both disappear.

Admins manage users at `/admin/users` (`templates/users_manage.html`) backed by the `/api/users` JSON API. Self-protection rules: cannot delete your own account, cannot remove admin from your own account. CLI bootstrap: `python ekko_trips_app.py create-admin`. Logins persist: `login_user(remember=True)` with a 365-day cookie, and when `FLASK_SECRET_KEY` is unset the generated key persists at `trip_data/secret_key` (gitignored) so restarts don't invalidate sessions.

### Share Links (read-only magic links)

`/s/<token>` logs a guest in as a synthetic viewer — user id `share:<token>`, never admin, never uploader — so relatives can see trips without an account. Because every mutation route is admin/contributor-gated, a leaked link exposes only viewing, which is why a long random token needs no password. Records live in `trip_data/share_tokens.json` (`{token: {label, trips_only}}`) and are managed from the Users page via `/api/share-links`.

- `load_user()` re-reads that file **on every request**, so deleting a token kills its live sessions instantly and flipping `trips_only` takes effect immediately.
- `trips_only` links additionally have `can_view_campgrounds` cleared.
- Unknown/revoked tokens render the login page with an explanatory error (403) rather than revealing anything.
- The token IS the credential, so `_redact_path()` truncates it to an 8-char prefix before it reaches the access log.

### Access Log

Who visited which page, including share-link guests — the identity lives only inside Flask-Login, so the host's own request log can't answer it. `_log_page_view` (an `after_request`) appends one JSONL record per **HTML GET** to `trip_data/access_log.jsonl`; assets, APIs, thumbs, tiles and static are skipped so one photo-heavy trip page doesn't bury the page views the log exists for. Auth transitions (`login`, `login_failed`, `share_login`, `share_revoked`, `logout`) are logged explicitly. Failed logins record the attempted username (never the password) — a run of them from one IP is the only signal that someone is guessing. Timestamps are UTC-aware so the browser can localize. `_log_access` never raises. `_prune_access_log()` drops entries past `ACCESS_LOG_RETENTION_DAYS` via temp-file + atomic replace. Viewed at `/admin/access-log`.

### Offline (Service Worker)

`/sw.js` (Flask route serving `static/sw.js` from root scope; login-exempt along with the `/offline` fallback page — a login redirect during SW install would cache the login screen as the offline page). Photos/thumbs (`/photo/`, `/thumb/`) are cache-first; pages/static/API GETs are network-first (online behavior identical to no-SW; cache is fallback only, so admins always edit fresh data). Redirected responses are never cached. Map tiles (OSM `*.tile.openstreetmap.org` + Esri `server.arcgisonline.com`) are cache-first in their own `ekko-tiles-*` cache (capped at 1000) — revisited tiles are instant and maps render offline; these are cross-origin no-cors so the responses are opaque and cached via a dedicated `tileCacheFirst` (the same-origin `cacheable()` guard rejects opaque). Other cross-origin (leaflet CDN) is still not intercepted. Bump `VERSION` in `sw.js` to flush caches after incompatible deploys. iOS standalone via `apple-mobile-web-app-*` metas + `static/manifest.json` + `static/icons/`.

### Photo System

- Photo metadata (captions, ordering) is stored separately from the files themselves.
- **`UPLOAD_DIR` lives OUTSIDE `static/`, and that placement is load-bearing.** Photos were originally in `static/uploads/` and served as `/static/uploads/...`; the `static` endpoint is login-exempt, so every full-size photo (and every not-yet-purged `.trash/` copy) was readable by anyone holding the link — and those links ship in the page HTML as `data-full`. Originals now serve only from **`GET /photo/<subpath>`**, the login-gated counterpart to `/thumb/`. Both routes go through `_resolve_photo_request()`, which applies three gates: `safe_join` (traversal), **no dot-prefixed path component** (this is what actually excludes `.thumbs/`, `.views/` and `.trash/` — `_allowed_file` only inspects the basename's extension, so a path *through* `.trash/` used to sail right past it), and `_allowed_file` (extension).
  - **Why the directory moved rather than just the URLs.** App-side gating cannot protect anything under the deployment's static root, because a front-end web server that maps `/static/` straight to disk never consults Flask — notably PythonAnywhere's static-files mapping. Adding a narrower `/static/uploads/` mapping pointed at an empty directory was tried and **did NOT take precedence** over the broader `/static/` one; PA kept serving the photos. Moving the directory out is the only fix that holds on every host, because there is nothing left at `static/uploads/` to serve. `_require_login_globally()` still 404s any `static` request under `uploads/` as a backstop, in case a stale directory reappears (an old backup restored over the tree, a half-finished migration).
  - **Keep it out of `trip_data/` too:** `sync-from-pa.sh` mirrors that directory with an optional `--delete` and syncs photos separately (`--photos`), so nesting them there would let a data-only sync wipe the library.
- **Three photo sizes.** Grids/slideshows render 480px JPEGs from `GET /thumb/<subpath>`; the **lightbox displays a 1600px derivative from `GET /view/<subpath>`** (`data-view` on the grid img); `GET /photo/<subpath>` is the untouched original, shown only when there's no `data-view` and always what the download button saves. Both derivatives are lazily generated by the shared `_ensure_derivative()` into `.thumbs/` / `.views/` subdirs beside the originals (mtime-keyed staleness, EXIF rotation baked in) — measured at ~10% of original bytes for the 1600px view. Add any new derivative dir to `DERIVATIVE_DIRNAMES` (drives `_remove_thumb`), to `backup.sh` / `sync-from-pa.sh` excludes, and to `sw.js`'s cache-first path list.
- **Undo-able deletes:** single-photo delete moves the file into a `.trash/` subdir (utime-stamped) and the client shows a "Photo deleted — Undo" toast wired to `POST .../photos/<file>/restore`. Caption/order/uploader metadata is kept on delete (inert while the file is absent) and scrubbed by `_purge_old_trash` when entries age past 7 days. "Remove All Photos" keeps its `confirm()` and its `rmtree` sweeps `.thumbs`/`.trash` too.
- **Favorites (poster heroes).** `trip_data/photo_favorites.json` is `{photo_key: true}`, keyed identically to captions. Admin-only, set from a ★ on each tile of `/trips/photos` (the bulk surface — the whole library in one grid, with an `?favorites=1` filter) or from the ★ in the lightbox chrome (where you actually notice a photo is good), both via `POST /api/photos/favorite`. The poster's two 2×2 hero cells deal from the marked set first. **Marking rather than inferring is the whole design:** no heuristic knows which photo is *good* — resolution, aspect and EXIF camera model are proxies for "taken with the nice camera" — and the sheet only needs a couple of dozen good photos, so the curation cost is an afternoon, once. `_collect_photo_pool()` carries `favorite` plus `curated` (from `_display_order()`: the photo leading a grid that was actually drag-reordered — implicit curation, used as the second-choice hero pool; a grid with no `photo_order` entry renders alphabetically ≈ chronologically, which is the *first* shot of a stay rather than the best one, so it yields None). Client side is `static/photo-favorite.js` (a page opts in by rendering `data-photo-key`/`data-favorite` on its imgs and setting `window.PHOTO_FAVORITES` from `is_admin`); `syncPhotoFavorite()` keeps the grid tile and the lightbox star from disagreeing, and writes are optimistic with a rollback + toast on failure.
- **People (poster prioritization).** `trip_data/photo_people.json` is `{photo_key: face_count}`, written ONLY by the offline `detect_people.py` scan (see Key Files) — no in-app UI writes it. `_collect_photo_pool()` collapses it to a boolean `people`, and the poster's hero deck ranks it between hand-starred favorites and `curated`: "is somebody IN it" is a fact a detector can answer, unlike "is it good", which stays hand-marked per the favorites rationale above. The app keeps the keys following their photos (same rename/prefix helpers as favorites: `_rename_people_key` on move, `_remove_people_by_prefix` on delete-all, `_remove_people_record` on trash purge, `_remap_json_keys` on sort) but scrubs a deleted photo's record rather than keeping it inert — a restored photo just rescans on the next run.
  - **Adding another per-photo metadata file means touching all of:** `_remap_indices_after_sort` in `trips.py` (or a stay date edit silently detaches metadata from its photo), `move-photo`, `_purge_old_trash`, the delete-all prefix sweeps, and `backup.sh`/`restore.sh` (or it doesn't travel between hosts). `_remap_json_keys` iterates `.items()`, which is why the store is a dict rather than a list.
- EXIF date taken is extracted via Pillow (`_photo_date_taken()`, cached per (path, mtime, size)) and displayed in the lightbox viewer.
- Upload supports both individual image files and zip files containing multiple images. Zip extraction filters out directories, hidden files, and non-image files.
- Drag-and-drop supports both within-grid reorder and cross-grid moves (campspot-to-campspot, campspot-to-event, etc.). Cross-grid moves call `POST /trips/<id>/move-photo` which relocates the file and updates captions/order.
- Upload areas detect whether a drag is an internal photo move or an external file upload and handle accordingly. When the destination grid is empty, the upload area itself serves as the drop target for photo moves (styled with red border instead of showing a separate empty grid indicator).
- When campspots or events are sorted by date (on add/update), photo directories and caption/order JSON keys are remapped to follow the new indices via `_remap_indices_after_sort()`. This uses temporary directory names to avoid collisions during the rename.

### Campground System

- `campgrounds.json` is a unified location database holding both `kind: "campground"` and `kind: "family"` entries, each with a stable `id`. Campspots reference entries by `campground_id`, and events reference family entries by `family_id`. Because references are ID-based, renaming an entry via the management page needs no propagation logic — existing references remain valid automatically.
- Custom stays (e.g. Airbnb, hotel) use `campground_id: null` and a free-text `custom_place` field. The frontend's `stayFieldsToPayload()` decides which fields to send based on whether the place text matches a known entry.
- Campspot edit forms use an autocomplete picker that fetches from `GET /api/campgrounds` (includes both kinds). Selecting an entry stores its `id` in a hidden field and auto-fills the state field. Family-kind entries are shown with a 🏠 prefix in the dropdown. When the user types free text that matches no entry, it's saved as `custom_place`.
- `trips.py:_load_locations_by_id()` is the single source of truth for resolving IDs to coordinates — prefers `driveway_location` for family-kind entries so stay markers don't collide with the red family house marker.
- **Deletes are reference-guarded.** `DELETE /api/campgrounds/<id>` returns 409 while any trip still points at the entry, listing the offending trips; `?force=1` overrides. Because references are by id, an unguarded delete fails *silently* — the campspot's `place` falls back to `custom_place or ""` and it loses its coordinates, leaving a blank row that plots nowhere. `trips.campground_references(id)` is the checker (covers both stay `campground_id` and event `family_id`).
- **Names are not unique and are not checked.** Campground names repeat constantly across states (7× "Lakeview Campground", 6× "South Fork Campground"; 286 duplicated names across 668 entries). An earlier uniqueness check on create/rename was unenforceable against the file's own data and only blocked legitimate adds. References are by `id`, so duplicates cost nothing.
- **The audit-evidence fields never reach the browser.** `waterfront_evidence` / `inclusion_evidence` are the source of truth in `campgrounds.json`, but no template or client script reads them and together they were ~4.6 MB of the map page. Both `_load_campgrounds()` and `/api/campgrounds/all` strip them. Safe because `PUT /api/campgrounds/<id>` merges from a **field whitelist**, so a UI save can't clobber a field the client never received. Keep that whitelist in mind before adding a new editable field — a field absent from it silently won't save.
- **Large text responses are gzipped** by the `_compress_response` `after_request` (HTML/JSON/CSS/JS over 4 KB). The campground map embeds the whole database inline, so it renders as ~9 MB of HTML that goes out at ~1.9 MB. Skips non-200s, already-encoded responses, and `direct_passthrough` (send_file) responses.

### Campground Inclusion Criteria

Entries must be a real, publicly-bookable, drive-in RV campground usable by the family's 23-ft RV ("EKKO"). Before adding one:
- **Access:** drive-in, passable by a normal vehicle (decent dirt/gravel is fine; hardcore offroad / 4WD-required disqualifies). No pad needed (grass is fine); hookups never required.
- **RV size:** at least some drive-in sites must fit a 23-ft rig. If the largest sites cap around 20 ft, exclude — EKKO can occasionally squeeze into a 20-ft spot but we don't rely on it (barring a genuinely special case).
- **Never add:** horse/equestrian campgrounds (a general campground that merely *offers* horse sites is OK); hike-in / tent-only / boat-in / cabin-only / group-only; fairgrounds that only allow camping during events.
- **Not a real transient campground — exclude even if it technically takes overnighters:** parks that are mostly seasonal/full-timer, residential / mobile-home-park, or workforce/long-term (e.g. gas-field worker housing); membership / club / sales-pitch parks (Thousand Trails, Encore, Bluegreen, Coast-to-Coast; Elks/Moose/Airstream-club lodges; timeshare "buy-in" resorts); casino/racetrack overnight lots.
- **Dead/missing official website is a strike** — treat a campground with no working official site as suspect, especially combined with thin/no reviews; don't add unless it's otherwise well-confirmed as currently operating.
- **Unrated / thinly-reviewed needs firsthand confirmation, not a guess.** An RV Life `star_rating` of 0 means *unrated*, and few/no reviews — not automatically excluded (public/government sites are legitimately lightly reviewed), but it removes your safety net. Before adding such an entry you must confirm the basics — fee/reservation model, drive-in RV access, RV-fitting site length, amenities, currently-operating — from a firsthand or authoritative source (official/agency page, campground map/photos, a dated trip report, or a directory with real specifics). If you can't confirm those facts, **skip it** rather than inserting a placeholder you'll have to walk back.
- **Every `note` claim must be sourced — never copy aggregator boilerplate.** Listing aggregators (snoflo, camping.org, campingroadtrip, mobilerving, etc.) auto-generate generic prose like "clean restrooms, hot showers, picnic tables, fire pits… reservations are required… popular among campers." That is filler, not data — do not lift it into a `note`. Prefer the operator's own page, the reservation system, campground photos/site maps, and firsthand reports. When an aggregator's prose disagrees with its own structured fields (e.g. prose says "reservations required" but the data field says "Reservations: No"), the structured field wins.
- **First-come-first-served:** always add a `note` saying so when there's no reservation system. **Consistency gate:** if a `note` asserts "reservations required," the record must carry a real booking channel — a reservation `website` (recreation.gov / reserveamerica / a state/agency portal) or a verified `phone`. A "reservations required" claim with no booking channel is self-contradictory and almost always wrong (it's usually a free FCFS site); resolve it before inserting, don't ship the contradiction. Many USACE / federal river and reservoir areas are free, primitive, and FCFS by default — assume FCFS unless a booking channel actually exists.
- **Dispersed sites:** drive-in dispersed sites may be added when encountered, but don't go out of the way to hunt them.
- **Ownership values:** `state` (state parks, state forests/SRAs/WMAs, state-DNR areas, and interstate-compact parks like Breaks), `federal` (USACE / USFS / NPS / BLM / Reclamation), `local` (county / town / city / regional or municipal authority), `private`, `hipcamp`. State-forest campgrounds are `state`, distinct from state parks. County land run by a private concessionaire is still `local`; a utility-run campground (e.g. Brookfield/PPL) is `private`.
- **Waterfront reflects RV-accessible sites only, and an on-water value must be *earned* with site-level proof.** Riverfront/lakefront cabins or tent-only/shelter sites do NOT qualify. The standard is a burden of proof, not a vibe — follow it exactly:
  - **Default down.** The value is `not waterfront` unless positive, named evidence upgrades it. "Couldn't confirm" always resolves *down* (to `*view` or `not waterfront`), never up. Absence of confirmation is never permission.
  - **Evidence that COUNTS** (any one promotes to an on-water value): an official per-site campground map/PDF showing pads at the shoreline; a rec.gov per-site `SHORELINE SITE: Y` flag; **satellite imagery at the pinned campground coordinate showing RV pads within ~1 pad-depth of the waterline**; or a dated firsthand photo of an RV site on the water.
  - **An open, unused apron to the water counts as on-water — the discriminator is a real *buffer*, not the ground cover.** What earns `lakefront`/`riverfront` is a pad with an open, unobstructed, walkable apron to the water — and that apron may be **sand, dune, OR grass**. Sand vs. grass is irrelevant: a pad sitting on an open sandy beach and a pad sitting on an open unused lawn that runs to the shore are the same case (a camper can walk an unobstructed path and put a boat in). The apron's **width does NOT downgrade**, and at a reservoir neither does drawdown — measure to the **beach/high-water edge, not the drawn-down waterline** — SUBJECT TO the distance bound below. Scattered trees that don't meaningfully block view or access do not disqualify. What DOES disqualify (a genuine separating **buffer**): a continuous treeline/vegetated screen; a developed or *used/populated* strip between site and water (road / parking / day-use beach lawn / picnic ground / cabins — "unused" is the operative word in the apron test); or an elevated **bluff/bench** the site sits atop with a graded slope down (climb-down, not walk-across). Those resolve to `lakeview` if the open view holds, else `not waterfront`.
    - **Distance bound (on-water vs `*view`):** the open apron earns on-water only when it is roughly the **campground's own frontage — within ~50 m / a site-depth or two** of the water (the functional test: a short, unobstructed walk you'd actually carry a kayak across). An open, visible, but genuinely *distant* span (e.g. ~150–250 m across a field) is a **view, not access** → `*view`. Don't let "open grass" swallow `lakeview`; that tier is exactly for set-back-but-visible sites.
    - (This generalized a rule that first only counted sand — which had corrected a CO sweep reading low-pool tiles as a wide beach "buffer," e.g. Jackson Lake — to the equivalent open-grass apron, per AWH 2026-06-14: ground cover is arbitrary, the buffer/use and the distance are what matter.)
    - **COASTAL special case — `coastal dunes` / `coastal woods`:** the one override of the dune/treeline-buffer + distance rules above. A campground sitting behind an **undeveloped shore dune field** (`coastal dunes`) or, on a Great Lake/ocean, set back in the **shore forest** (`coastal woods`) is **on-water even with NO line of sight and well beyond ~50 m**, PROVIDED the land between sites and water is the campground's **own undeveloped dune/forest with no other USE** (campers walk/boardwalk through it to the beach). The dune/woods is the coastal setting itself, not a buffer.
      - **`coastal dunes` applies on ANY body of water large enough to have built a genuine wind-formed dune field** — ocean, Great Lake, OR a large inland lake (Lake Winnipeg, Lake Manitoba, Great Salt Lake, etc.). Dunes only form where a big water body supplies enough fetch/wind/sand, so "large enough to have real dunes" is the self-limiting gate. The discriminator is a **genuine, substantial dune field** — satellite-confirmed hummocky/vegetated wind dunes (e.g. Grand Beach on Lake Winnipeg) — NOT merely a flat sandy beach, a single low foredune berm, or a mowed picnic lawn. A small pond or an ordinary lake beach with no true dune field does NOT qualify; judge those by the standard open-apron/buffer + distance rules (→ `lakefront`/`lakeview`/`not waterfront`). (AWH 2026-07-14: extended coastal dunes from Great-Lakes/ocean-only to any dune-building water body, correcting the MB sweep that wrongly downgraded dune-backed Lake Winnipeg parks.)
      - **`coastal woods` stays Great Lakes & ocean ONLY** (never inland water) — a set-back-in-the-forest, no-sightline call has no dune-field physical gate, so it's reserved for true marine / Great-Lakes shore forest.
      - STILL disqualifies for both (→ `*view`/`not waterfront`): a **road/highway** between camp and shore (US-41/US-31/M-25/PTH), a developed **day-use beach + parking complex**, a **cabin/residential strip**, or the loop genuinely inland with other land use between — those are real *uses*. Satellite look still mandatory (confirm the gap is the campground's own undeveloped dune/woods — not a road/lot/day-use strip — and for the inland case that the dunes are genuine wind dunes, not just beach sand); canopy/dune-blind + agency "on Lake <X> / beach access" supports it. The D.H. Day / Warren Dunes / Hoffmaster / Sleeping Bear / Pictured Rocks / Grand Beach case. (Originally AWH 2026-06-15, after a MI state sweep wrongly downgraded dune-backed Great-Lakes parks to not-waterfront.)
  - **Evidence that is FORBIDDEN as the sole basis**: marketing prose ("on the lake," "lakeside resort"); aggregator boilerplate or vague review snippets ("some sites near the water"); a brochure *overview* map (an icon merely *near* water); the campground's **name** ("Lakeview"/"Creekside"/"Riverbend"); or the mere presence of "lake/river access," a boat ramp, or a marina. A marina park whose pads sit uphill is `lakeview`/`not waterfront`, not `lakefront`.
  - **The satellite look is MANDATORY but its authority is ASYMMETRIC — it can veto, but it cannot be the sole confirmer in canopy.** Always pull the coordinate and look, but weigh it correctly: (a) when the imagery is *legible*, it is decisive and **overrides prose/brochure maps** — pads visibly set back from the water → downgrade (this is where it catches marinas, brochure-map pins, and "lake access" parks) — but an open unused **apron (sand, dune, or grass) within the distance bound** in front of the pad is NOT "set back" (see the open-apron rule above): a downgrade needs a real buffer (treeline, developed/used strip, or a bluff/bench the site sits atop), not just open sand/grass or a drawn-down waterline; (b) when the imagery is *illegible* — dense forest canopy, low-resolution/old base tiles, deep shade (common for Adirondack/boreal/remote sites where individual pads simply can't be resolved) — it can neither confirm nor deny, and "I couldn't see pads" is **NOT** grounds to downgrade. In that case defer to the higher-authority source: an **official per-site campground map** or **per-site reservation/`waterfront` data** is primary and a canopy-blind satellite does not override it. For established agency campgrounds (DEC/COE/USFS/NPS/state parks) that official per-site map almost always exists and is the authority — satellite is the cross-check, not the verdict. Still required: SOME qualifying source (legible-and-positive satellite, OR official per-site map, OR per-site reservation flag, OR dated firsthand photo) must confirm shoreline sites; if none does, default down.
  - **`*view` needs the same rigor** — only if some **RV** sites actually overlook water (confirmed, not assumed); else `not waterfront`. But note the **floor**: a pad on open ground (grass or beach) with the water *visible and unscreened* across that ground is at LEAST `*view` — it cannot be `not waterfront`, because nothing on open ground blocks the sightline. `not waterfront` for a water-adjacent site requires a real screen/buffer (treeline, building, berm), the site being genuinely far/inland, or the water not visible — not merely "set back across open grass."
  - **Record the proof in the `waterfront_evidence` JSON field.** Any on-water (or `*view`) designation must carry a one-line `waterfront_evidence` string on the entry itself, naming the artifact (e.g. "rec.gov site map: sites 12–15 on shore" / "satellite at 36.57,-93.30: pads at waterline"). In agent workflows this is a required structured-output field; a designation with no evidence string is written as `not waterfront`. **The field is the SINGLE audit record (NOT the commit message — that proved too easy to skip, GA 2026-06-17):** a non-empty `waterfront_evidence` means the entry has been waterfront-audited; an empty/absent field means it has NOT been audited. That one check is the whole answer — no need to also scan the `note`. Firsthand owner audits (`--AWH` in `note`) were backfilled with a `waterfront_evidence` string on 2026-06-17 (capturing the owner's pre-`--AWH` note text), so they too carry the field. **Keep this invariant:** whenever you record a firsthand `--AWH` waterfront call, also write a `waterfront_evidence` string, so the field stays the sole source of truth. The `apply_waterfront_audit.py` script writes the field from each result's `evidence`; keep a copy of the evidence in the commit message too for convenient `git log` grepping, but the JSON field is the source of truth.

### Campground Data Curation (state-by-state audit)

An ongoing effort adds campgrounds missing from `campgrounds.json`, worked systematically by state and by ownership/operator. **Git log is the progress record** — read recent commits to see which states/categories are done before continuing. Typical order per state: state (parks → forests/SRAs/WMAs) → federal (USACE / USFS / NPS) → private → local. (State + federal are largely done for VA / MD / DE / PA / WV.)

**Waterfront audit is a built-in sweep stage, not a separate pass.** The original pre-gate re-audit (re-verifying old `waterfront` values state by state) is **COMPLETE**. For every new state from here on, fold the audit's full strength into the sweep so entries land correct the first time (chosen approach, KS-style 2026-06-11). Per-state pipeline:
  1. detect (RV Life) → vet inclusion criteria → pin `location` → fetch elevation. While pinning, the research agent captures a structured waterfront **`lead`** — `{map_url, water_body, candidate_sites, note}`, the per-site campground map it already found plus any site numbers it saw near the water — and returns it. The lead is a head start for the audit, NOT a verdict (don't let it set `waterfront`);
  2. write the candidate entries with `waterfront: "not waterfront"` as a placeholder (don't guess from name/marketing/lead) **and an `inclusion_evidence` string capturing the add-time validity proof** (the operator/reservation-system source confirming it's a real drive-in RV campground — see the inclusion-audit paragraph below);
  3. run the **same** `audit/waterfront_audit_instructions.md` subagents over the just-added ids (~8 ids per batch), **carrying each entry's `lead` into its batch object** so the audit verifies the already-found per-site map instead of re-discovering it (seam optimization, AWH 2026-06-14) — the satellite look stays mandatory and the gate still decides; satellite + per-site-map/rec.gov check + coord verification happen here at full strength. **Run the audit batches SEQUENTIALLY, one subagent at a time** (default for every sweep stage): parallel batches exhaust the session limit and lose in-flight work — only fan out in parallel on an explicit per-stage user OK (GA 2026-07-15, after a parallel WA-audit wave hit the session limit twice);
  4. apply with `python3 audit/apply_waterfront_audit.py <results.json>` (sets `waterfront`, fixes mis-pinned `location`/`elevation_meters`, **and writes each entry's `waterfront_evidence` from the result's `evidence` string**);
  5. the `waterfront_evidence` JSON field is the durable audit record (empty/absent = not audited; `--AWH` note = audited). Echo the per-entry evidence in the commit message too ("Audit all NN <ST> waterfront designations") for convenient `git log` grepping, but the field is the source of truth — do not rely on the commit alone.
  Methodology, subagent instructions, and apply script live in `audit/` (see `audit/README.md`). Skip the satellite look only for entries with no water anywhere near (pure in-town RV parks, fairgrounds) — they stay `not waterfront` by default-down. You may run the audit as its own commit right after the add commit, or thread it into the add; either way it is mandatory before a state is "done."

**Inclusion (validity) audit is a built-in sweep stage too — recorded at ADD time, not a separate pass** (standard since 2026-06-25, after a cabins-only park, Canoe Creek SP, was found to have slipped into the DB from an early less-rigorous import). It verifies the entry is a *real, currently-operating, drive-in RV campground fitting a 23-ft rig* — catching cabins-only / tent-only / hike-in-boat-in / group-only / day-use-only / fairground-event-only / membership / residential-seasonal / closed / under-23ft / duplicate entries. Unlike the waterfront audit it does NOT need a separate subagent pass during a sweep: the add-stage research agent is **already the authority** that decides keep/drop (it reads the operator/agency page + reservation-system per-site list to vet inclusion in pipeline step 1), so it simply **emits a one-line `inclusion_evidence` string for each entry it keeps** and writes it into the entry (pipeline step 2). The `inclusion_evidence` JSON field is the durable record: **non-empty == inclusion-audited & confirmed a valid campground; empty/absent == NOT audited** (same invariant as `waterfront_evidence`). Discipline: the proof must name an **authoritative source** (DCNR/agency "Stay" page, ReserveAmerica/recreation.gov per-site site-type list, the operator's own site) — **aggregators (snoflo, camperalerts, campscanner, thedyrt/camping.org summaries) routinely INFLATE cabin-only/day-use parks into fake "RV sites"; never confirm a keep from an aggregator alone**, and when an aggregator conflicts with the operator the operator wins. For **retroactive** re-vetting of a state added before this discipline (PA was the completed pilot — 169 entries, 11 removed), run the separate `audit/inclusion_audit_instructions.md` subagents and apply with `python3 audit/apply_inclusion_audit.py <results.json>` — it stamps `inclusion_evidence` on confirmed keeps and **reports** the `remove`/`review` candidates without auto-deleting (a human reviews the remove list before excising the `{ }` block by id; check `trip_data/` for `campground_id` references first).

**Detection data sources (RV Life is the workhorse):**
- **RV Life** (`campgrounds.rvlife.com`) — Algolia app `H0LPZK92QJ` (search key is inline in any park page's HTML: `algoliasearch('H0LPZK92QJ', '<key>')`), index `park`. Useful fields: `price_level` (int 0–4 = number of `$` signs), `star_rating` (0–5 user rating — note `avg_rate` is the nightly price, NOT a rating), `park_type` (`commercial`/`state`/`county`/`city`/`regional`/`dnr`/`coe`/`usfs`/`national`/`military`), `cg_name`, `city_name`, `region_abbvr`, `_geoloc`. `region_abbvr` is NOT facetable — pull a state via `insideBoundingBox=[[minLat,minLng,maxLat,maxLng]]` then keep `region_abbvr == <ST>`.
- **Good Sam** — Algolia index `gs-ml-cb-assets-prod` (app `VT01MNVCP5`); search key is a 2-hour secret fetched from an AppSync `getCampgroundSearchAuthSecret` query (use Python `urllib` for the POST — the sandbox blocks `curl` POST). Carries triple ratings and a `campground.type` `MEMBERSHIP_PARK` flag (unreliable — confirm membership independently).

**Private (commercial) campgrounds:** add only if RV Life `price_level` ≤ 2 ($ or $$) AND `star_rating` ≥ 4 AND not a membership park; then vet each per the inclusion criteria (real transient RV campground, not seasonal/residential/workforce/club; dead-website strike) and set waterfront from the RV sites via the evidence gate (default `not waterfront`; on-water only with a satellite/site-map confirmation, never from a "lakeside"/"riverfront" name or marketing).

**Local campgrounds:** detect via RV Life `park_type` in {county, city, regional} PLUS a name-scan of the commercial/state buckets for government keywords (county / township / municipal / regional / borough) to catch mislabels (RV Life mis-tags some county/authority parks as commercial). `park_type == dnr` is a state DNR area (state, not local). Do NOT apply the ≥4★/≤$$ gate to local — public government campgrounds are inherently cheap and lightly reviewed; include any confirmed local-government drive-in RV campground and just record the RV Life star/price in the note. Confirm the operator is genuinely local government.

Mechanics:
- **id:** `max(existing id) + 1`; ids are permanent and never reused.
- **Append, don't re-dump:** append entries preserving the file's 2-space indentation; never rewrite the whole file (a full `json.dump` reorders keys / reformats floats / re-escapes unicode and churns the diff). Validate with `json.load` after each batch. To remove an entry, excise just its `{ }` block by id (no braces appear inside values).
- **Fields:** `id`, `kind: "campground"`, `name`, `location` ("lat,lng"), `elevation_meters`, `state`, `ownership`, `waterfront`, `waterfront_evidence` (the waterfront audit proof string; present iff waterfront-audited — see the Waterfront "Record the proof" bullet), `inclusion_evidence` (the validity-audit proof string; present iff inclusion-audited — see the "Inclusion (validity) audit" paragraph), `website`, `phone`, `note`.
- **Coordinates:** pin `location` to the actual campground, not the park HQ/entrance — verify via allstays / recreation.gov / reserveamerica / campsitephotos / official campground-map PDFs (RV Life `_geoloc` is often off by several km).
- **Elevation:** Open-Meteo DEM — `https://api.open-meteo.com/v1/elevation?latitude=<lat>&longitude=<lng>` (comma-separated lists for batch); store meters in `elevation_meters`.
- **`waterfront` vocabulary:** on-water `lakefront`/`riverfront`/`creekside`/`pond`/`bayfront` (+ `coastal dunes`/`coastal woods`); view-only `lakeview`/`riverview`/`bayview`; else `not waterfront`. Any non-`not waterfront` value must clear the **evidence gate** in the inclusion-criteria "Waterfront" bullet above (default-down, forbidden sources, mandatory satellite look, recorded `waterfront_evidence`) — never assign from name/marketing/reviews alone.
  - **`coastal woods` does NOT count as waterfront for the map's "On the water" quick filter** (AWH 2026-07-25). That filter's `ON_WATER` set in `campground_map.html` is `bayfront`/`lakefront`/`riverfront`/`creekside`/`pond`/`coastal dunes` — sites genuinely at the water's edge. `coastal woods` is a set-back-in-the-trees designation with no sightline, so it's excluded there even though the curation rules still treat it as an earned on-water *designation* (i.e. it's a real category with its own evidence bar; it just isn't "on the water" for filtering). Don't "fix" the asymmetry by adding it to `ON_WATER`.
- **Confirm the campground & operator:** reservation directories also list day-use, cabin-only, group, and boat-in/hike-in facilities — verify a drive-in RV campground before adding. Many reservoirs have a USACE dam but state- or USFS-run campgrounds — credit the actual operator, not the dam owner. Don't fabricate phone numbers — verify or omit.
- **Note attribution:** the `note` is a shared record. When editing a note already tagged with someone's initials (e.g. `--AWH`), keep their text intact and append your change as a distinct segment with your own marker (`--Claude`); don't fold your edits into theirs.
- **URLs belong in `website`, not `note`.** The reservation/official site (recreation.gov, reserveamerica, a state/agency portal, the campground's own domain) goes in the `website` field — newline-separated if several, deduped by domain. Keep website URLs out of `note` prose: write "Reservable online" rather than "Reservable via recreation.gov". Two exceptions stay as prose: a *negative* reservation fact ("FCFS — not on recreation.gov", "book via Campspot, not recreation.gov") and a dead/suspect official domain recorded as a caveat. Source citations (a blog/listicle/video the recommendation came from, e.g. a `campingprepper.com` page) are attributions, not the campground's site — don't move them into `website`; de-URL to a bare name if practical.
- **Prefer deep, campground-specific URLs** over generic portal homepages, and ideally carry BOTH the official park page AND a direct deep reservation link (so booking is one click, no hunting). Deep formats: recreation.gov → `/camping/campgrounds/<id>`; ReserveAmerica → `.../campgroundDetails.do?contractCode=XX&parkId=<id>` or `/explore/<park>/<ST>/<id>/<unit>/campsite-booking`; **US eDirect portals (ReserveOhio, ReserveFlorida, ReserveCalifornia)** → `<frontend>/#!park/<PlaceId>` where PlaceId comes from the citypark API: ReserveOhio `https://ohiordr.usedirect.com/Ohiordr/rdr/fd/citypark`, ReserveFlorida `https://floridardr.usedirect.com/FloridaRDR/rdr/fd/citypark` (each record has `Name`/`Latitude`/`Longitude`/`PlaceId`; match by name+geo). Frontends: ReserveOhio `https://reserveohio.com/OhioCampWeb/#!park/<id>`, ReserveFlorida `https://reserve.floridastateparks.org/Web/#!park/<id>`. Note: `camp.in.gov` redirects to ReserveAmerica (`indianastateparks.reserveamerica.com`), and `goingtocamp` (WI) is Aspira — neither has the clean US eDirect API. **Illinois (ExploreMoreIL)** migrated to a Tyler backend and its OLD `camp.exploremoreil.com/location/<id>` deep links are DEAD (every path 302-redirects to the homepage — don't use them, and fix any you find). Current working format: `https://recreation.exploremoreil.com/IllinoisWeb/Default.aspx#!park/<PlaceId>` (hash route, no redirect). The citypark API is `https://il-rdr.recreation-management.tylerapp.com/IllinoisRDR/rdr/fd/citypark` (`EntityType=="Park"` records carry `Name`/`PlaceId`/geo; its `apiurl` base is inline in the `camp.exploremoreil.com/` HTML). **Verify per-park, not just via the API:** the API lists a park if ANYTHING there is reservable (camping/cabin/shelter), and its place-info URLs have collisions — confirm by fetching the park's own DNR page (`dnr.illinois.gov/parks/camp/park.<slug>.html` or the `dnrhistoric.illinois.gov` site page) and reading the real `#!park/<id>` it links. A DNR camp page that shows only the boilerplate `#!park/3` (Illinois Beach, present on every page) means that park's camping is FCFS (e.g. Pyramid, Cave-in-Rock, Big River SF, the Illinois-River-backwater SFWAs). See [[reference_usedirect_deep_reservation_links]].
- **Git:** commit campground edits directly to `master` (solo data repo; no feature branch unless asked); push only when asked.
- **GitHub auth (HTTPS push):** auth is automated via `git-ask-pass-pat.sh` (tracked) + a `GITHUB_PAT` in the gitignored `.env` at the repo root. The askpass script loads `GITHUB_PAT` from that `.env` if it isn't already in the environment, so `git push` needs no manual `source`. One-time per clone, point Git at it (writes machine-local `.git/config`, an absolute path, so it isn't committed):
  ```
  git config core.askPass "$(pwd)/git-ask-pass-pat.sh"
  ```
  Then create `.env` with `export GITHUB_PAT=<token>`. After that, `git push origin master` authenticates with no prompt. When the PAT expires, just update it in `.env`. (If `core.askPass` is unset or `.env`/PAT is missing, push falls back to failing on credentials — the user runs `! git push origin master` themselves.)

### Map Marker Color Scheme

- **Campspot markers:** Navy (`#002868`) circles/dots with white border across all maps. On trip detail maps, 24px numbered divIcons. On main trips map, circleMarkers sized by visit count.
- **Event markers:** Gold (`#c9a84c`) on all maps. Star divIcons on trip detail maps, circleMarkers on main trips map.
- **Home/family markers:** Red (`#bf0a30`) background with white house SVG icon on all maps (trip detail, trips map, campground maps).
- **Family markers on trip detail:** Only shown when a stay or event from the trip is within 80km (haversine distance).
- **Trip detail straight-line route:** built day-by-day. For each date: morning location (stay you woke at, or HOME) → events/waypoints sorted by time (untimed = noon) → evening location (stay you sleep at, or HOME). Loops on excursion days, direct trails on travel days. Drawn as the dashed `#002868` "Straight route" overlay; removed from the map automatically when the GPS track renders.
- **Auto-fallback to straight track:** when the GPS data doesn't actually cover the trip, the GPS layer is silently skipped and the dashed straight-line route stays as the only polyline. Triggered when the `/track` fetch fails/returns nothing in-window, or a strict (completed trips) / relaxed (in-progress trips) anchor-proximity gate fails. There is no manual "force straight" toggle — these heuristics are the only mechanism. Full gate logic and the trip-61 / trip-90 rationale are in the comment above the gate in `trip_detail.html` (search `Auto-fallback: skip the GPS layer`). (Older `trips.json` entries may still carry a vestigial `force_straight_route: true`; it is read by nothing and survives only until the trip is next saved.)
- **GPS track overlay:** `/api/trips/<id>/track` fetches OwnTracks-style points from a timeline service (`TIMELINE_API_TOKEN` + primary `TIMELINE_TID`, optional `TIMELINE_TID_ALT`). When alt is configured, the endpoint fetches BOTH tids over the trip window and stamps each ping with `tid: "primary"|"alt"`; `_select_track_per_day` then picks one tid per day (see "Per-day tid selection" below). Cached on disk gzipped at `trip_data/track_cache/<id>.json.gz` (dual-tid tracks compress ~6x; all cache I/O goes through `_read_track_cache`/`_write_track_cache`/`_delete_track_cache`/`_track_cache_exists`, which read a legacy plain `<id>.json` transparently and rewrite it as `.json.gz` on next persist — the `.json.gz` extension also keeps `restore.sh`'s `*.json` parse-check from choking on gzip bytes); trips ended >1 day ago serve from cache permanently. Legacy untagged caches stamp `tid: "primary"` on read (one-shot migration). Spurious pings (cell-tower fixes, single jumps) are filtered upstream by a separate pre-processing app. Server-side `_enrich_with_timezone()` (optional `timezonefinder` dep, idempotent on cache read) attaches per-ping IANA `tz` so the per-point markers' popups can show local-at-recording-location time.
- **Per-day tid selection (`_select_track_per_day`):** when both tids are configured, the endpoint picks one tid per day for the trip window (anchor-encounter count as the proxy for "which phone traced the trip today", with override / single-tid / continuity / day-1 fallbacks). The full per-day algorithm (cases A–E), the cleaned-view-decides / raw-points-filter split, and the pad-day handling are documented in the `_select_track_per_day` docstring. Shared with `_load_trip_track_for_detection` so detect-stops and the polyline see the same chosen pings.
- **Admin tid override (`tid_overrides`):** trip-level dict `{"YYYY-MM-DD": "primary"|"alt"}` that forces the selector's choice for that day regardless of the heuristic. The Track Source modal on trip detail (admin-only desktop button next to Detect Stops) lists each trip day with the auto pick + per-tid ping counts + a radio for [auto / force primary / force alt]; Save PUTs diffs to `/api/trips/<id>/tid-overrides` and refetches the polyline. The "Force alt" radio is disabled when `TIMELINE_TID_ALT` is unset.
- **Sub-day tid windows (`tid_windows`):** whole-day `tid_overrides` are too coarse when the normally-chosen phone is only missing pings for a *short span* the other phone covered (a brief gap on the primary `tid` present on the alt). `tid_windows: [{start,end,tid,note}, ...]` forces a specific tid (`"primary"|"alt"`) for a sub-day time range — `start`/`end` are local-time `"YYYY-MM-DDTHH:MM"` strings in the home tz (same convention + `_trip_local_to_tst` helper as `bad_track_windows`). Parsed by `_tid_window_tsts`; last matching window wins on overlap. Applied by the shared `_apply_tid_choice` helper, which decides each ping's wanted tid as the window override (if the ping falls in one) else the per-day `tid_choices` value — so both the polyline (`api_trip_track`) and detect-stops (`_load_trip_track_for_detection`) honor it and see the same corrected track. No UI — edit `trips.json` by hand (like `bad_track_windows`). Entries with an unknown/missing `tid` are silently skipped; specifying `tid:"alt"` where `TIMELINE_TID_ALT` is unset just yields a gap.
- **Manual ping overrides (admin):** trips carry three optional override lists, all applied server-side in `_apply_overrides` inside `api_trip_track` (see that function's comments for exact behavior): `suppressed_pings: [tst,...]` (dropped from the track; gray dashed ghost layer for admins), `relocated_pings: [{tst,lat,lon},...]` (lat/lon rewritten so the polyline follows; amber ghost layer with a line back to the original), and `bad_track_windows: [{start,end,note},...]` (off-trip time ranges as local-time `"YYYY-MM-DDTHH:MM"` strings interpreted in the home tz via `_trip_local_to_tst`, whose pings are dropped). Admin clients pass `?admin=1` to get pings tagged (`suppressed`/`relocated`/`bad_window` + `original_lat`/`original_lon`) instead of filtered/rewritten silently, powering the click-to-undo ghost layers; cache stays raw, overrides computed on serve. Detect-stops applies the same overrides via `_load_trip_track_for_detection`. The suppress/relocate UI (Select-pings toolbar: Suppress, Center selected, drag-to-move) lives in `trip_detail.html`; `bad_track_windows` has no UI — edit trips.json by hand. The polyline gap-fills the resulting holes through the trip's anchors (see "Frontend track rendering") rather than drawing a straight line across. Endpoints under API Routes.
- **Frontend track rendering:** the GPS overlay is the polyline of every returned ping inside the trip window (sorted by timestamp). The window's lower bound is `HOME_START_TIME` (manual) / the server-provided `home_auto_start_tst` (from `_find_home_boundary_tsts`, in the `/track` payload) / start of `TRIP_START` local day, in that order; upper bound mirrors with `HOME_END_TIME` / `home_auto_end_tst` / start of the day after `TRIP_END`. Pings outside that window are dropped from both the polyline and the per-point markers. No blackout/radius suppression. Markers for stays, events, home, and family render independently of the polyline. The polyline also gap-fills uncovered periods with the day-by-day route anchors (`routeStops`, gated by `GAP_FILL_MIN_S` for interior gaps) and pads one ping outside each cut for the "leaving/arriving home" legs (gated by `BOUNDARY_PAD_MAX_S`); the mechanics and the trip-87 rationale live in the `Gap-fill the polyline` / boundary-pad comments in `trip_detail.html`. When the GPS track loads, the dashed straight-line route is removed from the map (still toggleable via the layer control).
- **Overview trip routes (main trips map):** every trip's driven line, drawn together on `/trips/map` as a toggleable "Trip routes" overlay — one color for all trips (`#002868` with a white casing, mirroring the detail map's GPS polyline), because at that zoom the lines overlap constantly and 90+ hues read as noise; a click-popup names the trip instead. Rendered with `L.canvas` in a dedicated `routePane` (z-index 350, below every marker pane) so a line can never eat a campspot dot's click.
  - **Precomputed and cached, not derived per request.** `GET /api/trips/routes` serves `{trip_id: [[lat,lng], ...]}` — one continuous polyline per trip — from `trip_data/trip_routes.json` (gitignored, regenerable). Turning raw pings into the drawn line runs per-day tid selection + home-boundary detection, and the whole library is ~100k pings across 92 trips — doing that on every landing-page hit is repeated work whose answer only changes when the trip or its track does. Measured: ~3 s cold for the full library, ~50 ms warm.
  - **Cache entries rebuild lazily** when their signature drifts, so there is nothing to remember to run after editing a trip. `_trip_route_signature()` hashes the track-cache file's mtime+size **and the whole raw trip record** — hashing the record wholesale rather than naming fields means a newly-added override kind can't be forgotten and silently serve a stale line. It also folds in whether the trip is currently in progress (see the coverage gate below). `python ekko_trips_app.py rebuild-routes [--force]` is a warm-up for after a deploy; deleting the file is always safe.
  - **Built from `_clean_track_points()`** — the same view the detail map's polyline and the home-boundary detector use — then cut to the same window (`_trip_window_cuts()` mirrors the frontend's `computeTripWindow()` precedence: manual `home_start_time`/`home_end_time` wins, then the auto boundary, then full local days). That shared path is what keeps the two maps from disagreeing about where a trip went; verified at 86 of 87 trips matching the detail-map window's endpoints within 5 m.
  - **The detail map's auto-fallback gate is ported, not skipped.** `_track_covers_trip()` is a Python port of the `Auto-fallback: skip the GPS layer` gate in `static/trip-detail/map.js` (strict anchor-proximity, relaxed only while a trip is in progress). A trip the detail map refuses to draw a GPS line for must not get one here either — 9 of 92 trips are rejected today. **The difference: there a failed gate leaves the dashed straight-line route; here it means no line at all.** Note this is about a trip with no usable track *at all* — a wholly synthetic anchors-only line would be an itinerary drawn as if it were a record. It does **not** conflict with connecting gaps inside a trip that does have a track (above): there the GPS is the line and the connector spans a hole in it.
  - **One continuous line per trip — a gap never breaks it.** An earlier version split the line across long unreported stretches to avoid drawing a road that was never driven; **a trip with a hole punched in it reads as broken rather than as honest, so gaps are now always connected (AWH 2026-07-27) — don't reintroduce the split.** Gaps are filled the way the detail map fills them: `_trip_route_stops()` is a port of that map's `routeStops` builder (the day-by-day morning-location → timed-events → evening-location walk, skipping future dates), and any anchors falling inside a gap are spliced in so the connector follows where the trip actually went. Interior gaps only pull anchors in past `TRIP_ROUTE_GAP_FILL_MIN_S` (90 min, mirroring the detail map's `GAP_FILL_MIN_S` — keep the two in step) so routine sparse OwnTracks logging doesn't add detours; leading/trailing anchors splice unconditionally (the leaving-home and coming-home legs), but never one whose clock time hasn't arrived yet. **Anchors are a refinement, not a requirement** — a gap with none in it still connects, straight and possibly very long (trip 47 carries a 347 km connector). Measured effect: every stay now lies within 5 km of its own trip's line (148/148, up from 146/152 when the line could break).
  - **Simplified.** Douglas-Peucker at `TRIP_ROUTE_SIMPLIFY_M` (100 m — sub-pixel until ~z12) cuts ~100k pings to ~30k vertices, ~200 KB gzipped for the whole library; `_simplify_latlon()` projects to meters first so the tolerance means the same thing east-west as north-south.
  - Fetched **after** the map paints (the map is fully usable without it), and home-only trips are filtered for non-admins exactly as `trips_map()` filters them, so a hidden trip can't reappear as a line.
- **Per-point GPS markers (admin-only, and the gate is on BUILDING them):** each ping gets a small clickable circle (radius 3) inside `gpsPointLayer`, hidden until zoom ≥ `GPS_POINT_MIN_ZOOM` (14). Click shows local-at-ping time and lat/lng. Toggling the GPS track in the layer control also toggles the dots. **`syncGpsPoints()` has always hidden these from regular users, but the markers used to be constructed for everyone** — so a non-admin paid the full cost of a layer they could never see, on a page that doesn't even load the `overrides.js` tooling those markers feed. That was most of the wait before the dashed route flipped to the real line on a long trip (trip 92: ~14k in-window pings; the per-ping `toLocaleString` with a named `timeZone` alone measured ~1.4 s on desktop Node, worse on a phone, on top of 14k `circleMarker` allocations). Construction is now behind `IS_ADMIN`, and the popup content is built **on open** rather than up front, so admins skip the formatting cost too. Everything downstream reads the published globals defensively (`window.__gpsPointMarkers || []` throughout `overrides.js`), so an empty layer is a complete answer for a regular user. Same per-capability principle as the `{% if is_admin %}` script loading in `trip_detail.html` — keep new per-ping work on the same side of that line.
- **Z-index layering on trip detail:** the suppressed/relocated override ghost layers render in a dedicated `overrides` pane (zIndex 700) above Leaflet's markerPane (zIndex 600) so the admin can always click through to unsuppress/unrelocate even when the override sits at the same coords as a stay or family marker. Within markerPane the divIcon ordering is Home (1000) > Family (900) > Stays (800) > Events (default).
- **Trip detail marker clicks are layout-dependent** (see "Trip Detail Map ↔ Card Interaction"): on the two-column layout they scroll to the corresponding card and carry no popup (a hover tooltip names them); on the stacked single-column layout they open a popup instead. Family-visit events at the same family location collapse into one shared marker via `familyVisitGroups`; its click scrolls to the earliest visit's card / opens a popup listing every visit there.

### Trip Detail Layout

Two-column grid (map left, cards right) when `trip.timeline` is non-empty; single-column when truly empty. The map column uses `position: fixed` (not sticky — sticky jitters during scroll); `syncMapColumnPosition()` mirrors the placeholder's `left`/`width` onto the fixed wrapper on load/resize/header-height-change but **never on scroll**. A `.trip-header`-measuring IIFE publishes `--trip-header-height` so the fixed map can anchor below it. Below the 900 px breakpoint the grid collapses to one column and `syncMapColumnPosition()` clears its inline writes so CSS resets aren't fought.

### Trip Detail Map ↔ Card Interaction

**Two-column only.** Clicking a marker scrolls the cards column to the corresponding card via `scrollToCard(cardId)`, which subtracts `--site-top-height` and `--trip-header-height` plus a 16 px gap from the card's `getBoundingClientRect()` Y. Card IDs: `stay-{idx}`, `event-{idx}`, `#home-card-start` (home start). Grouped family-visit markers pick the first sorted visit whose card actually rendered. The reverse (clicking a card `setView`s the map on its marker and pulses it) is also two-column only.

**Single-column (≤900 px, where the map stacks above the cards) replaces both with popups.** Following focus across a stacked layout is jarring in both directions — a marker tap scrolls the page out from under the map you just tapped, and a card tap moves a map that's off-screen. So on that layout the map answers in place: marker clicks open a trips-map-style popup (name, place, dates/nights or time, site/description, plus a "View details ›" link that scrolls to the card — the one map→card jump the reader actually asked for), and card clicks don't touch the map. `isSingleColumnLayout()` in `static/trip-detail/map.js` is the single breakpoint check, evaluated **per interaction** so rotating the device takes effect without a reload.

Popups are opened as standalone `L.popup(...).openOn(map)` rather than `bindPopup`, deliberately: binding installs its own click handler, which would pop the popup on the two-column layout too. `openMarkerPopup()` also calls `closeTooltip()` first, because Leaflet opens tooltips on click on touch devices and the two would stack. Popup "View details" links are wired on `popupopen` (delegated over `a[data-card]`), keeping the generated HTML free of inline event attributes.

### Trip Detail Timeline Cards

- Stay cards always render with a body. Event cards (regular events, waypoints, family-visits) go `.bare` whenever there's nothing to put in the body — i.e., the card has no photos AND either it's a waypoint/family-visit OR its description is empty. Bare cards render as just the colored circle + header, transparent background, no body. The "Upload Photos" button stays visible; admins also get an Edit button that opens the shared modal. The body still exists in the DOM for admins so the photo-grid can serve as a cross-card drop target — `body.photo-dragging .event-card.bare .event-body` reveals it absolutely-positioned during a drag without shifting layout. **The cross-grid drop handler keeps `.bare` in sync with the photo count on both sides of the move**: when a photo lands on a bare card the handler removes `.bare` (and reveals the previously-hidden "Remove All Photos" button) so the body stays visible after `dragend` clears `photo-dragging`; symmetrically, when the source card is left with no photos it re-applies `.bare` (and re-hides the button) using the same predicate the Jinja template uses on initial render — waypoint/family-visit OR no description. Without that pairing a dragged-out last photo would leave the source body sitting open and empty, and a dropped-in photo would disappear the moment the drag ended.
- **Split multi-night stays**: when a stay spans multiple nights AND at least one event falls on a *strictly interior* day (`arrival < date < departure`), `_make_trip()` emits one timeline copy per night. Each copy carries `copy_num`/`copy_count`. Photo bucketing assigns each photo to the closest-by-EXIF-time copy (rep time = `(arrival + copy_num - 1) at 20:00`); photos without EXIF time fall into copy 1. Copy 1 keeps DOM id `stay-{idx}`; copies 2+ use `stay-{idx}-{N}`. Inline edit form, stay details, campers, notes, and "Remove All Photos" render only on copy 1. Photo grids carry `data-stay-idx="{idx}"` on every copy so `saveGridOrder()` can concatenate filenames across all grids belonging to one stay.
- **Home cards**: `.event-card.bare.home-card` renders at the start and end of the timeline. The `.home-time-display` span shows the manual `home_start_time`/`home_end_time` (server-rendered) when set, else the GPS-derived time appended client-side as `· HH:MM (auto)` for admins or `· HH:MM` otherwise. The auto time is the `home_auto_start_tst`/`home_auto_end_tst` the `/track` response carries (computed by the Python `_find_home_boundary_tsts`); the client only formats and displays it, it doesn't recompute it. Admin Edit prompts are framed as overrides ("GPS-derived time is X; set a manual override only if that looks wrong").
- **Vertical timeline axis**: all timeline circles are 2 rem × 2 rem inside a header with `padding: 1rem 1.25rem`, so the circle center is always at X = 2.25 rem. A `.cards-column::before` pseudo draws a 2 px gray line through those centers; cards (`z-index: 1`) hide the line behind their backgrounds, circles (`z-index: 2`) paint above. Bare cards are transparent so the line shows through.

### Stop Detection (Admin)

Admin + desktop-only feature on the trip detail page. The **Detect Stops** button in `.trip-header` scans the trip's GPS track for dwell-time clusters not already represented by a stay/event/family location, classifies each as a waypoint (≤30 min) or event (longer), and returns them as advisory suggestions; the admin's selection is POSTed to `/api/trips/<id>/accept-stops`, which creates each via `add_event` with `needs_vetting: true` forced on server-side. Reverse-geocoding runs client-side (1 req/sec, Nominatim policy) with a progress banner and the "Create selected" button disabled until it finishes; closing the modal aborts the run via `AbortController`.

**On-road auto-uncheck:** `_reverse_geocode` returns `on_road: true` when Nominatim's primary hit is `class=highway` with `type in _ON_ROAD_HIGHWAY_TYPES` (motorway/trunk/primary/secondary/tertiary/residential/unclassified/living_street/road + `_link` variants — excludes `service`, `track`, footways). Detect-stops rows tagged this way render dimmed with an "on road · likely traffic" tag and the checkbox defaults to unchecked; the centroid being in the roadway is almost always a traffic jam / stop light rather than a real stop. The signal is free — read off the existing reverse-geocode response, no extra request. Admin can still opt-in by re-checking the box.

**Per-row mini-map:** each detect-stops row carries a small satellite-imagery preview (Esri World_Imagery, 110×80 px) fit to the cluster's ping polyline with a red centroid marker, so the admin can see at a glance whether the cluster sits in a parking lot, at a pull-off, or on a road. The endpoint returns `display.coords` (per-ping lat/lng list) for the cluster; `_initStopMiniMap` in `trip_detail.html` draws the Leaflet map. Lazy-init via IntersectionObserver — 20+ rows would otherwise spin up 20 maps at once for the ~5–8 visible at a time. Re-init on geocoding re-render (rows whose map was already live get an immediate re-init so the visible map doesn't blink empty); not-yet-initialized rows get re-observed. All instances are `.remove()`-d in `closeDetectStops`.

The full pipeline — cluster radius/duration tunables and their calibration, suppressed/relocated exclusion, trip-window narrowing, at-home/near-home classification, anchor-aware streak selection, manual-override precedence, and the known-location/at-home drops (incl. the trip-61/62/87 rationale) — is documented in code, not duplicated here: see the constant comments (`STOP_*`) and the docstrings/comments on `_detect_stops`, `_load_trip_track_for_detection`, `_find_home_boundary_tsts`, `_drop_stops_at_known_locations`, and `api_detect_stops` in `ekko_trips_app.py`.

`needs_vetting` is a boolean field on events. `true` items render with a dashed amber outline and a "Needs review" badge on the timeline card, plus a dashed amber ring on the map marker — mirroring on every surface so the admin can find them. The flag is cleared by *any* PUT to the event: both the inline and modal save handlers inject `needs_vetting: false` into the payload, so simply opening + saving the edit form is the act of vetting. The field defaults to `false` in `_make_trip()` for older trip records that predate the field, so existing data renders unchanged. Tunables (radius/duration constants) live at module level in `ekko_trips_app.py` near the helpers.

**Trip-boundary calculation has one implementation.** `_find_home_boundary_tsts()` in `ekko_trips_app.py` is the sole home-boundary detector (its docstring carries the full algorithm and the SINGLE-SOURCE-OF-TRUTH contract). It feeds two consumers: (1) `api_trip_track` returns `home_auto_start_tst` / `home_auto_end_tst` in the `/track` payload, which the frontend uses for both the polyline window cuts (`computeTripWindow`) and the home card's "(auto)" time — the frontend never recomputes; (2) detect-stops calls it directly. Manual `trip.home_start_time` / `trip.home_end_time` win over the auto values on both. **Do not reintroduce a JS reimplementation** — a prior one (`findHomeBoundaryTimes`) drifted and was deleted. The constants (`STOP_NEAR_HOME_M`, `STOP_AT_HOME_CENTROID_M`, `STOP_HOME_BOUNDARY_LOCK_S`, `TRACK_NEAR_STAY_KM`) live only on the Python side.

### Local HTTPS

`ekko_trips_app.py`'s dev runner serves HTTPS by default — required for browser features that need a secure origin, most importantly the Geolocation API used by the map picker's 📍 button. `_dev_ssl_context()` reuses a **persistent self-signed cert** at `trip_data/dev_cert.{crt,key}` (gitignored), generated once via Werkzeug's `make_ssl_devcert`. Persistence matters because `debug=True`'s auto-reloader restarts the process on every code change, and the old `ssl_context='adhoc'` minted a *new* cert each boot — so the browser exception you accepted no longer matched and the cert warning returned on every edit. With the stable cert you accept it once and it survives reloads. Falls back to `'adhoc'` if the cert can't be generated (needs `cryptography`/`pyopenssl` in the venv). Pass `--http` to fall back to plain HTTP (fine on `localhost`, which browsers treat as a secure context even over HTTP; LAN devices need the HTTPS path). Production hosts (PythonAnywhere) handle TLS at the platform level and ignore this code path.

### Backups (data bundle helper)

The app's "database" is the gitignored JSON + photos, deliberately kept as separate small files (small isolated writes, secrets in their own `users.json`, `track_cache/` per-trip) — see the multi-file rationale rather than merging into one blob. Two repo-root scripts bundle/restore that set for copying between hosts (e.g. PythonAnywhere → local):

- **`backup.sh`** → writes `backup/ekko-backup-<ts>.tar.gz` (the `backup/` dir is gitignored). Includes `users.json`, `home.json`, `trip_data/{trips,captions,photo_order,photo_uploaders,photo_favorites,share_tokens}.json`, `trip_data/access_log.jsonl`, and `trip_data/track_cache/`. Excludes `campgrounds.json` (tracked in git — comes via `git pull`), `trip_data/secret_key` + `dev_cert.*` (machine-local), and `.thumbs`/`.views`/`.trash` (regenerable). `--with-photos` also bundles `photo_uploads/` (minus the derivative caches and trash); `-o <path>` overrides the output. Only existing members are archived, so a fresh install bundles cleanly.
- **`restore.sh <tarball>`** → refuses anything not containing `trip_data/trips.json` (guards against restoring the wrong archive), snapshots current data to `backup/pre-restore-<ts>.tar.gz` first (reversible), extracts over the repo, then validates every restored `*.json` parses (and points at the rollback snapshot on failure). `-y` skips the confirm prompt. **Stop the running app before restoring** so nothing writes mid-restore.

Full flow: on the source host run `./backup.sh [--with-photos]`, download the tarball, then locally `./restore.sh <tarball>` + `git pull` (for `campgrounds.json` + code).

### Deploying to PythonAnywhere

`./deploy-to-pa.sh` ships whatever is on GitHub to the live app: `git pull` on PA, then `touch` the ekko WSGI file. **The reload is not optional** — PA keeps Python modules and Jinja templates loaded in the worker, so a pull alone changes disk without changing what the site serves. `-n` dry-runs; `--no-reload` pulls only. The host runs two web apps (ekko + timeline); only ekko's WSGI file is ever touched.

**SSH is key-only and least-privilege** (since 2026-07-27; no PA account password is stored on this machine). Two passphrase-less keys, each pinned in PA's `~/.ssh/authorized_keys`:
- `~/.ssh/pa_deploy_ed25519` → `command="…/pa-deploy-remote.sh",restrict`. The wrapper (in this repo, running **on PA**) accepts exactly `status` / `deploy` / `deploy-no-reload` from `$SSH_ORIGINAL_COMMAND` and refuses everything else, so the key can't get a shell. Never interpolate `$SSH_ORIGINAL_COMMAND` into a command there — that would hand back the arbitrary execution the forced command removes. Because the wrapper is deployed *by* the deploy it implements, editing it takes one extra deploy to take effect.
- `~/.ssh/pa_sync_ed25519` → `command="/usr/bin/rrsync -ro <repo>",restrict`, used by `sync-from-pa.sh`. Read-only, so **rsync paths are relative to that root** (`$PA_HOST:/trip_data/`, no `/home/...` prefix).

**Adding another machine:** give it its OWN keys rather than copying these — `authorized_keys` is append-only, and a per-machine key can be revoked by deleting one line if that laptop is lost. On the new machine, `ssh-keygen -t ed25519 -N "" -f ~/.ssh/pa_sync_ed25519` (and `pa_deploy_ed25519` if it should deploy), then append the pubkeys with the same `command="…",restrict` prefixes over an interactive password login — **`>>`, never `>`**. Re-run the refusal tests afterwards. Also delete the now-unused `PA_PW` from that machine's `.env`: it's gitignored and per-machine, so it survives the switch and is a stored account password no script reads. The SD-card / USB build needs nothing — it never talks to PA.

Verified at install: an arbitrary command on either key is refused, and an rsync upload gets "sending to read-only server is not allowed". PA doesn't document `command=` support (their sshd is stock OpenSSH 8.9) — re-test if they change hosts. **Password auth remains enabled server-side** and `sshd_config` isn't ours, so this bounds what a stolen key can do; it doesn't stop someone who has the account password. Interactive work (rollbacks, reading live edits) deliberately still needs a password login.

**Capturing live UI edits:** `./capture-pa-edits.sh` is the round trip for edits saved through the admin UI on PA (campground manage page, roadside stops on the map). Those live only in PA's working tree — no commit, no backup — so this reads them down over the read-only sync key, validates the JSON, commits, pushes, then has PA drop its now-redundant copy (`reconcile`) and deploys. `-n` dry-runs; `--no-push` stops after the local commit.

It refuses rather than guessing when the two sides could both be right: local uncommitted changes to those files, PA's HEAD not an ancestor of local HEAD, or **any local commit since PA's HEAD that already touched those files** — that last one is the silent-loss case, where copying PA's working copy down would revert a local sweep commit PA hasn't pulled yet (deploy first, then capture). `reconcile` is the only thing that ever discards a live edit, and it's guarded by content, not trust: the working file's blob hash must equal the blob in the upstream commit, so a byte of difference (someone saved again mid-run) makes it refuse and leave that edit for the next capture.

**The one real hazard:** `campgrounds.json` and `roadside.json` are tracked in git **and** written by the live admin UI, so PA's tree is legitimately dirty whenever a campground was edited there, and those edits exist nowhere else. The script aborts before pulling when live edits collide with incoming commits; resolve by bringing the live edits **down** (diff over an interactive login, apply here, push) — never `git checkout --` on PA. After the reload it polls `/login` (login-exempt, so 200 proves Flask booted and rendered) and fails loudly; it deliberately does **not** auto-roll-back, because `git reset --hard` would destroy those same uncommitted live edits.

## API Routes

### Trip/Campspot/Event CRUD
- `POST /api/trips` — create trip (empty, no default campspot)
- `PUT/DELETE /api/trips/<id>` — update/delete trip
- `POST /api/trips/<id>/stays` — add campspot
- `PUT/DELETE /api/trips/<id>/stays/<idx>` — update/delete campspot
- `POST /api/trips/<id>/events` — add event
- `PUT/DELETE /api/trips/<id>/events/<idx>` — update/delete event
- `GET /api/trips/<id>/track[?admin=1]` — returns `{points: [...], home_auto_start_tst, home_auto_end_tst}`. `points` is the GPS track; the two tsts are the auto-detected trip boundary from `_find_home_boundary_tsts` (single source of truth for the polyline window + home-card "(auto)" time; either may be `null`). Degenerate cases (trip has no dates, or no API token and no cache) still return a bare `[]` array, which the frontend treats as no points + no boundary. Admin pages pass `admin=1` so each ping carries `suppressed`/`relocated` flags + `original_lat`/`original_lon` for relocated pings (instead of being filtered/silently rewritten); the boundary is computed on the cleaned view regardless of the flag, so every viewer gets the same window
- `GET /api/trips/routes` — every visible trip's precomputed, simplified GPS line for the overview map: `{trip_id: [[lat, lng], ...]}` (one continuous polyline per trip; trips with no drawable line are omitted rather than returned empty). Home-only trips are filtered for non-admins. See "Overview trip routes"
- `POST/DELETE /api/trips/<id>/suppress-pings` — mark / unmark `tst`s as suppressed (body `{tst: [...]}`); idempotent
- `POST /api/trips/<id>/relocate-pings` — set lat/lon overrides (body `{items: [{tst, lat, lon}, ...]}`); replaces existing entries by `tst`
- `DELETE /api/trips/<id>/relocate-pings` — clear overrides (body `{tst: [...]}`)
- `PUT /api/trips/<id>/tid-overrides` — admin-only; body `{date: "YYYY-MM-DD", value: "primary"|"alt"|null}`. `null` clears that day's override. Returns the resulting overrides dict.
- `GET /api/trips/<id>/tid-choices` — admin-only; returns `{tid_choices, tid_overrides, counts, alt_configured}` where `tid_choices` is what the per-day selector would pick **ignoring overrides** (so the Track Source UI can render "Auto (would pick X)"). `counts` is per-day per-tid raw ping counts.
- `POST /api/trips/<id>/detect-stops` — admin-only; scan the trip's GPS track for dwell-time clusters not already represented by a stay/event/family location. Returns a list of suggestions, each with a `display` block (for the modal) and an `event` block (the exact payload `/accept-stops` will feed into `add_event`). Reverse-geocodes one stop per second so the call can take tens of seconds.
- `POST /api/trips/<id>/accept-stops` — admin-only; body `{events: [<event payload>, ...]}`. Creates each as a new event/waypoint with `needs_vetting: true` (server always forces the flag on, regardless of payload).

- `POST /trips/<id>/events/<idx>/upload` — upload event photo or zip file

Star/unstar a poster hero. `photo` is the storage subpath every photo URL already carries, so one endpoint covers stays and events on every surface; the key is resolved through `_resolve_photo_request` so a nonexistent photo 404s rather than accumulating a dead metadata entry

### Campground CRUD
- `GET /api/campgrounds` — lightweight `{id, name, state, kind}` list (for autocomplete picker; includes both kinds)
- `GET /api/campgrounds/all` — full data (admin, for management page); strips `waterfront_evidence` / `inclusion_evidence`
- `POST /api/campgrounds` — create entry (auto-assigns next id; accepts `kind`; family entries may carry `driveway_location`). No name-uniqueness check
- `PUT /api/campgrounds/<int:id>` — update entry by id, merging from a **field whitelist** (so audit-evidence fields survive); no name-propagation needed, references are id-based
- `DELETE /api/campgrounds/<int:id>[?force=1]` — delete entry by id; **409 while any trip references it** (body carries `references`), `force=1` overrides

### Weather Finder (Open-Meteo forecast search)
- `GET /campgrounds/weather` — the page (admin-only via `_require_admin_page()`)
- `GET /api/weather-finder/lookup?q=<name>` — admin-only campground name search backing the by-name forecast lookup. Matched server-side and capped at 20, prefix matches first; `/api/campgrounds` would mean shipping ~12.9k rows to the browser to type into
- `GET /api/weather-finder/forecast?id=<id>` — admin-only. **Every forecast day for one campground, no distance limit and no filters** — you named it, so you want its forecast rather than a verdict on it. Shares the search's grid cells and cache both ways, so a lookup inside an already-searched area is free and also warms that cell
- `POST /api/weather-finder/search` — admin-only. Body: `mode` (`range`/`cooler`/`warmer`), `max_miles`, `min_high`/`max_high` (range mode), `delta_f` (relative modes), `weekends_only`, `dry_only` + `max_precip_in`, `waterfront_only`, `sort` (`distance`/`temp`/`rain`/`waterfront`), optional `lat`/`lng` origin (defaults to `home.json`). Returns campgrounds grouped with their matching days, plus `eligible` / `considered` / `fetched` / `from_cache` so the page can say what was actually checked — "no matches" and "no matches in the part we looked at" are different answers. **429 is passed through** as the provider's rate limit, not swallowed: a partly-fetched search returns fewer matches, which reads exactly like "there aren't any"

### Federal Availability (recreation.gov / RIDB)
- `GET /api/ridb/search?q=X` — search federal campgrounds by name (campground-view gated)
- `GET /api/ridb/availability?facility=<RIDB FacilityID>&start=YYYY-MM-DD&end=YYYY-MM-DD[&fit_ft=]` — per-night availability for sites EKKO fits (both dates inclusive; `fit_ft` defaults to `DEFAULT_FIT_FT`). Campground-view gated

## Conventions

- Private Python functions prefixed with `_`
- Routes organized by section with comment headers in `ekko_trips_app.py`
- Photo keys use format `{trip_id}/{stay_idx}/{filename}` (campspots) or `{trip_id}/events/{event_idx}/{filename}` (events)
- Photo order keys: `{trip_id}/{stay_idx}` or `{trip_id}/events/{event_idx}`
- Trip IDs are permanent auto-incrementing integers; display numbers are computed from chronological position
- No frontend build step — all JS/CSS is inline in templates except the shared map picker (`static/map-picker.js`, `static/map-picker.css`), the shared photo lightbox (`static/lightbox.js`, `static/lightbox.css`, markup partial `templates/_lightbox.html`), `static/photo-favorite.js`, and the `static/trip-detail/` modules
- The lightbox is shared by trip detail and the trips map. A page opts in by including `_lightbox.html` plus that CSS/JS pair. `openLightbox(img)` alone pages through the clicked img's `.photo-grid` siblings; `openLightbox(img, {photos, onClose})` lets a caller supply its own set. Per-photo extras are read off the img: `data-full` (original to swap in for the thumb), `data-caption` (fallback when the photo isn't in a `.photo-item` carrying a `.caption-text` span), `data-trip-href`/`data-trip-name`/`data-trip-date` (shows the trip card — omit on pages already scoped to one trip), `data-place-name` (the card's second line — the campspot/event/waypoint name alone; the kind is deliberately not labeled). The trip card is styled to match the landing page's `.latest-trip-banner` / `.on-this-day` cards (white card, colored left rule, right-justified CTA pill) — keep them in sync. It centers along the top via auto margins (leaving `transform` free for the hover lift), capped at `min(720px, 100vw - 200px)` so a centered box can't reach the close/download cluster; ≤700px it drops below those buttons at full width and sheds the date to protect the names. `trips_map.html` derives the place from the pool's `card` index against `TRIPS` — no extra server data
- `_collect_photo_pool()` carries each photo's `caption` (one `captions.json` read per build, and the caption endpoints invalidate the pool so edits show up immediately). It deliberately does NOT carry the EXIF date taken — that needs a Pillow open per file, which is why the trips-map lightbox shows no date badge
- The data model uses "stays" internally (code, JSON keys, API routes) but the user-facing term is "campspot/campspots"
- The waterfront field in data is called "waterfront" but displayed to users as "Proximity to Water"
- Pluralization: all counters use singular when count is exactly 1, plural otherwise (including 0). In JS use `!== 1`, in Jinja use `== 1`. Never use `> 1` as it mishandles zero.
- Jinja `tojson` is configured with `sort_keys: False` to preserve Python dict insertion order (important for legend ordering)
