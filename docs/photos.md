# Photo system

Moved out of CLAUDE.md on 2026-10-25 to keep that file small. Treat this as part of the project instructions: read it before touching the code it describes.

- Photo metadata (captions, ordering) is stored separately from the files themselves.
- **`UPLOAD_DIR` lives OUTSIDE `static/`, and that placement is load-bearing.** Photos were originally in `static/uploads/` and served as `/static/uploads/...`; the `static` endpoint is login-exempt, so every full-size photo (and every not-yet-purged `.trash/` copy) was readable by anyone holding the link — and those links ship in the page HTML as `data-full`. Originals now serve only from **`GET /photo/<subpath>`**, the login-gated counterpart to `/thumb/`. Both routes go through `_resolve_photo_request()`, which applies three gates: `safe_join` (traversal), **no dot-prefixed path component** (this is what actually excludes `.thumbs/`, `.views/` and `.trash/` — `_allowed_file` only inspects the basename's extension, so a path *through* `.trash/` used to sail right past it), and `_allowed_file` (extension).
  - **Why the directory moved rather than just the URLs.** App-side gating cannot protect anything under the deployment's static root, because a front-end web server that maps `/static/` straight to disk never consults Flask — notably PythonAnywhere's static-files mapping. Adding a narrower `/static/uploads/` mapping pointed at an empty directory was tried and **did NOT take precedence** over the broader `/static/` one; PA kept serving the photos. Moving the directory out is the only fix that holds on every host, because there is nothing left at `static/uploads/` to serve. `_require_login_globally()` still 404s any `static` request under `uploads/` as a backstop, in case a stale directory reappears (an old backup restored over the tree, a half-finished migration).
  - **Keep it out of `trip_data/` too:** `sync-from-pa.sh` mirrors that directory with an optional `--delete` and syncs photos separately (`--photos`), so nesting them there would let a data-only sync wipe the library.
- **Three photo sizes.** Grids/slideshows render 480px JPEGs from `GET /thumb/<subpath>`; the **lightbox displays a 1600px derivative from `GET /view/<subpath>`** (`data-view` on the grid img); `GET /photo/<subpath>` is the untouched original, shown only when there's no `data-view` and always what the download button saves. Both derivatives are lazily generated by the shared `_ensure_derivative()` into `.thumbs/` / `.views/` subdirs beside the originals (mtime-keyed staleness, EXIF rotation baked in) — measured at ~10% of original bytes for the 1600px view. Add any new derivative dir to `DERIVATIVE_DIRNAMES` (drives `_remove_thumb`), to `backup.sh` / `sync-from-pa.sh` excludes, and to `sw.js`'s cache-first path list.
- **Undo-able deletes:** single-photo delete moves the file into a `.trash/` subdir (utime-stamped) and the client shows a "Photo deleted — Undo" toast wired to `POST .../photos/<file>/restore`. Caption/order/uploader metadata is kept on delete (inert while the file is absent) and scrubbed by `_purge_old_trash` when entries age past 7 days. "Remove All Photos" keeps its `confirm()` and its `rmtree` sweeps `.thumbs`/`.trash` too.
- **Favorites (poster heroes).** `trip_data/photo_favorites.json` is `{photo_key: true}`, keyed identically to captions. Admin-only, set from a ★ on each tile of `/trips/photos` (the bulk surface — the whole library in one grid, with an `?favorites=1` filter) or from the ★ in the lightbox chrome (where you actually notice a photo is good), both via `POST /api/photos/favorite`. The poster's two 2×2 hero cells deal from the marked set first. **Marking rather than inferring is the whole design:** no heuristic knows which photo is *good* — resolution, aspect and EXIF camera model are proxies for "taken with the nice camera" — and the sheet only needs a couple of dozen good photos, so the curation cost is an afternoon, once. `_collect_photo_pool()` carries `favorite` plus `curated` (from `_display_order()`: the photo leading a grid that was actually drag-reordered — implicit curation, used as the second-choice hero pool; a grid with no `photo_order` entry renders alphabetically ≈ chronologically, which is the *first* shot of a stay rather than the best one, so it yields None). Client side is `static/photo-favorite.js` (a page opts in by rendering `data-photo-key`/`data-favorite` on its imgs and setting `window.PHOTO_FAVORITES` from `is_admin`); `syncPhotoFavorite()` keeps the grid tile and the lightbox star from disagreeing, and writes are optimistic with a rollback + toast on failure.
- **People (poster prioritization).** `trip_data/photo_people.json` is `{photo_key: face_count}`, written ONLY by the `detect_people.py` scan (see Key Files) — no in-app UI writes it; the app *triggers* the scan on upload but never does the detection itself. `_collect_photo_pool()` collapses it to a boolean `people`, and the poster's hero deck ranks it between hand-starred favorites and `curated`: "is somebody IN it" is a fact a detector can answer, unlike "is it good", which stays hand-marked per the favorites rationale above. The app keeps the keys following their photos (same rename/prefix helpers as favorites: `_rename_people_key` on move, `_remove_people_by_prefix` on delete-all, `_remove_people_record` on trash purge, `_remap_json_keys` on sort) but scrubs a deleted photo's record rather than keeping it inert — a restored photo just rescans on the next run.
  - **Automatic people scan on upload.** Both upload routes (campspot + event, single file and zip) end with `_queue_people_scan(keys)`, so a photo carries its `people` flag within seconds of landing instead of waiting for someone to remember the scanner. A daemon thread coalesces queued keys over `PEOPLE_SCAN_DEBOUNCE_S` (5 s) — a 40-photo drag-drop arrives as 40 separate POSTs and must not become 40 process starts — then shells out to `detect_people.py --only <keys>` in batches of `PEOPLE_SCAN_MAX_BATCH`, and calls `_invalidate_photo_pool()` so the flag doesn't wait out the pool's TTL.
    - **A subprocess, not an import, and that's a memory decision.** OpenCV costs ~70–100 MB resident; imported here it would be paid by every worker that ever handled one upload, for the life of that worker, whereas a one-shot process pays it for a couple of seconds. It also keeps the "the web app never imports cv2" invariant literally true, and degrades well — on a host with no opencv the subprocess simply fails and the app is unaffected.
    - **`_people_scan_python()` probes for the interpreter rather than assuming one**, because "which python has opencv" differs per host: PA has it in the app's virtualenv, this dev box has it in `~/.virtualenvs/ekko` while the repo's own `ekko_trips_venv` doesn't (a `pip install --user` a venv can't see is the usual way that happens). Each candidate (`sys.prefix/bin`, then `sys.executable`, then `python3` on PATH) is asked to `import cv2, numpy, PIL` and the first that can wins; the answer is cached, including a `None` that logs one warning and disables the feature. `sys.prefix` is tried before `sys.executable` because under a WSGI server the latter can be the server binary.
    - Known gap, accepted: keys live only in memory, so an app restart inside the debounce window loses that batch. A plain `python detect_people.py` is incremental and picks up anything missed. `EKKO_AUTO_PEOPLE_SCAN=0` disables the trigger on a host that shouldn't scan (partial photo mirror).
  - **Photo storage is keyed by POSITION, so every renumbering must move the photos.** A campspot's photos live at `photo_uploads/{trip}/{idx}/` and an event's at `photo_uploads/{trip}/events/{idx}/`, with the five metadata stores keyed on the same shape — so inserting an item mid-trip, deleting one, or editing a date so the list re-sorts renumbers everything above it. `trips.py` funnels all of that through **one** function, `_apply_photo_index_mapping(trip_id, kind, mapping)`, taking `old_idx -> new_idx` (`None` = the slot is gone: directory removed, metadata keys dropped). `_remap_indices_after_sort` and `_remap_indices_after_delete` are the two thin callers. Directory moves are two-phase through `_tmp_{idx}` names because a shift-down maps 3→2 while 2 still exists. **Keep them unified:** delete used to have its own implementation (`_shift_photo_dirs`) that moved directories without touching metadata, so a delete would have left every caption and favorite pointing at the neighbouring item's photos.
    - **`trips.UPLOAD_DIR` names the root and must stay equal to `ekko_trips_app.UPLOAD_DIR`.** When the library left `static/`, `trips.py` kept the dead path; every `os.path.isdir()` returned False, so directory renames silently no-op'd while the metadata remap went ahead, detaching captions/favorites from their photos (fixed 2026-09-01). `tests/test_photo_index_remap.py` pins it across insert/delete/date-edit for both kinds.
    - **`repair_photo_metadata.py`** re-links drifted records BY FILENAME (a basename is unique within a trip; the script verifies that and skips anything ambiguous or occupied). Dry-run by default, `--apply` backs up first, idempotent, and it refuses to run on a partial photo mirror (`MIN_EXPECTED_PHOTOS`) — run it on PA. The 2026-09 drift is repaired; keep it for any recurrence.
  - **Adding another per-photo metadata file means touching all of:** `trips._PHOTO_METADATA_FILES` (the single list `_apply_photo_index_mapping` walks — miss it and the metadata silently detaches the next time an index moves), `move-photo`, `_purge_old_trash`, the delete-all prefix sweeps, and `backup.sh`/`restore.sh` (or it doesn't travel between hosts). `_remap_json_keys` iterates `.items()`, which is why the store is a dict rather than a list.
- EXIF date taken is extracted via Pillow (`_photo_date_taken()`, cached per (path, mtime, size)) and displayed in the lightbox viewer.
- Upload supports both individual image files and zip files containing multiple images. Zip extraction filters out directories, hidden files, and non-image files.
- Drag-and-drop supports both within-grid reorder and cross-grid moves (campspot-to-campspot, campspot-to-event, etc.). Cross-grid moves call `POST /trips/<id>/move-photo` which relocates the file and updates captions/order.
- Upload areas detect whether a drag is an internal photo move or an external file upload and handle accordingly. When the destination grid is empty, the upload area itself serves as the drop target for photo moves (styled with red border instead of showing a separate empty grid indicator).
- When campspots or events are sorted by date (on add/update), photo directories and caption/order JSON keys are remapped to follow the new indices via `_remap_indices_after_sort()`. This uses temporary directory names to avoid collisions during the rename.

## `detect_people.py`

- `detect_people.py` — Batch scanner: finds photos with people in them (OpenCV YuNet face detection; tiny ONNX model auto-downloaded once to `trip_data/models/` with a pinned sha256) and writes `trip_data/photo_people.json` (`{photo_key: face_count}`, one entry per SCANNED photo — 0 means "looked, nobody there", absent means "not scanned yet", which is what makes re-runs incremental). The web app never imports cv2 — it only reads the JSON (`people` flag in `_collect_photo_pool()`, ranked by the poster's hero deck) and **runs this script as a subprocess when a photo is uploaded** (see "Automatic people scan on upload"), which is what keeps new photos flagged without anyone remembering to scan. `--only <key> ...` is that path: it skips the directory walk and scans exactly the keys named. Results are merged into the JSON at write time (re-read, then apply this run's deltas) rather than dumping the dict loaded at startup, so a scan racing the app's own edits to that file — a delete scrubbing a record, a move renaming a key — can't clobber them. A manual run stays the backstop for anything the auto-scan missed (an app restart inside the debounce window): **run it where the full photo library lives** (PA via an interactive login: `pip install --user opencv-python-headless`, then `python3 detect_people.py`; or locally after `./sync-from-pa.sh --photos`) — this machine holds only a partial photo mirror, which is also why `--prune` is off by default (pruning against a partial mirror would delete the records for every photo the machine doesn't have) and why `--prune` is refused together with `--only`. Faces are the signal, so a person photographed from behind or at great distance won't register; that's acceptable because a false negative just leaves the photo in the general pool, and a false positive merely promotes a photo that was otherwise a coin flip. Verified on trip 92 (70 photos, 38 flagged, spot-checked clean, ~0.2 s/photo).
